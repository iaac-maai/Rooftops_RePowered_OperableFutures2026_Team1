A. CURRENT NORTH STAR: WHAT TO BUILD
================================================================================

PROJECT TITLE
Roofscapes (Re)Powered — AI-Assisted Rooftop Solar and Building-Demand Matching in Barcelona.

PROJECT TYPE
A short 3-month architecture / AEC / smart-construction studio project. We are already PAST the midterm as of 14 November 2026, with final review around 10–17 December 2026. This is not a multi-year platform. Prefer one credible, end-to-end demonstrator over a broad collection of half-implemented systems.

RESEARCH QUESTION
How can AI-assisted building electricity-demand estimation improve the planning and use of limited rooftop solar resources among a small cluster of Barcelona buildings, considering environmental value, economic feasibility, and socially responsible benefit distribution?

PROPOSED DELIVERABLE
A reproducible pre-installation decision-support prototype using:
  1) REAL Barcelona urban/building context (public rooftop estimates, building functions, candidate participants);
  2) a conventional established PV simulator/output (PVGIS 6, and Barcelona's municipal solar resource map as a reference);
  3) one properly trained and benchmarked AI model for hourly ELECTRICITY demand, trained on accessible measured reference data or, if necessary, on explicit physics-based synthetic simulation outputs;
  4) understandable hourly matching of PV generation against demand for one host roof and 3–5 participating buildings;
  5) comparison of individual solar use, conventional collective shares, and AI-informed pre-agreed hourly shares;
  6) transparent estimated environmental / cost / social-allocation indicators;
  7) a lightweight visual interface connected to the results, preferably reusing an existing website if practical.

PRIORITY ORDER
  Primary: environmental contribution — locally used PV energy, grid-import changes, indicative avoided operational emissions.
  Feasibility criterion: economics — PV capex/O&M, electricity price assumptions, participant savings, simple payback ranges.
  Responsibility criterion: social benefit — who benefits, solar-coverage shares, fairness proxies; NO unsupported demographic/vulnerability claims.
  Essential technical character: AEC and smart construction — site geometry, roof physical constraints, building uses, performance-led pre-construction planning.
  Essential intellectual character: AI plays a REAL and evaluated role, not an ornamental chatbot or a relabeling of deterministic solar calculations.

DECIDED SCOPE
- One host rooftop, approximately three to five neighboring potential consuming buildings.
- Small Barcelona cluster, not a citywide deployment. Prior 3x3 Eixample blocks are useful as research context, not mandatory detailed computation scope.
- ONE primary trained AI demand model (XGBoost recommended), with a baseline and meaningful validation.
- Existing engineering tools do PV modeling. Do NOT retrain an AI model just to perform available PV calculations.
- No required authenticated APIs/API keys and no real-time cloud dependency. Public downloadable files, locally cached data and manually exported PVGIS files are preferred.
- Synthetic building schedules are accepted due to limited public access to actual occupancy and electricity data, but provenance and limitations MUST be explicit.
- The prototype must be able to conclude that collective sharing does not improve environmental performance in some settings.

WHAT THIS IS NOT
Not a working electricity market, real energy community with legally signed contracts, real-time dispatch controller, city-scale digital twin, peer-to-peer power transfer mechanism or structural rooftop certification.

3) Crucial user correction: SURPLUS
An earlier assistant initially characterized the project as identifying buildings with excess solar generation to distribute to others. The user explicitly corrected this: in many dense urban settings, roof PV may cover only a PORTION of a building's own electricity consumption, with the grid supplying the rest. It is not safe to assume routine excess generation.

Key clarification from subsequent analysis:
- A collective self-consumption scheme may distribute shares of PV production across participants; participants do not need to individually produce more than they consume.
- A building can simultaneously draw solar-allocated power and remaining grid electricity.
- Hourly PV production and load must be compared. Annual energy totals alone cannot determine actual hourly self-consumption.
- Do NOT assert "surplus is always rare" as an established universal finding. Surplus likelihood varies by roof size, demand, hours and installed PV.
- In regulatory terminology some collective self-consumption arrangements may be categorized as having surplus even if actual exported electricity is small. Keep legal terminology distinct from physical excess.

Illustrative example from the earlier chat (NOT real data):
  Office load = 100 kWh during one hour; PV production = 30 kWh during that hour.
  Office uses 30 kWh PV + 70 kWh grid; no necessary surplus.
  Hypothetical shared case: office demand 100 kWh, residence 25 kWh, commercial 20 kWh; allocate 15/10/5 kWh PV; remaining loads from grid. The example demonstrates allocation, not measurable environmental improvement over host-only use.

4) Critical logical flaws previously identified
(a) Changing PV allocation does not create solar energy. If all PV is already consumed by the host, sharing may redistribute financial benefit but not reduce aggregate grid import or emissions. Show genuine incremental advantage relative to host-only and fixed-share baselines.
(b) AI cannot necessarily change legally effective allocation coefficients dynamically in real time. Spanish collective self-consumption rules were discussed as allowing pre-agreed hourly coefficient profiles with restrictions on updating them; verify current official rules rather than implementing a live controller. Earlier discussion mentioned a four-month minimum between certain revisions; treat this as regulatory research pending confirmation.
(c) Nearby in a map is not automatically legally eligible. Examine the actual applicable distance/electrical and administrative constraints if making legal claims; the earlier research discussion mentioned a revised 5 km provision for specified installations, but do NOT hardcode legal limits without verification. The user's test cluster may use a conservative 500 m radius as a design convenience, not as a blanket law.
(d) Building opening hours and occupancy schedules are NOT measured electricity consumption. HVAC, equipment, standby loads, climate, floor area, server loads and efficiency create large differences.
(e) Barcelona city "energy" figures can refer to total final energy (including fuels/heat), while the model targets ELECTRICITY only. Do not mix denominators or imply the grid is 100% fossil.
(f) Solar forecasting and roof suitability maps already exist: do not sell a trivial clone of PVGIS or Barcelona's municipal solar resource map as novel AI.
(g) Building owners need an incentive to participate; quantify preliminary participant benefit and fairness. No need to set up actual contracts.
(h) A solar sharing arrangement is NOT by itself a legally constituted "renewable energy community". Use accurate terminology.
(i) A synthetic-data model can learn the simulation or assumptions generating those labels, not automatically learn true Barcelona meter behavior. Report this limitation.

5) New central framing
"AI-assisted solar-demand matching" or "data-constrained rooftop solar planning" rather than "surplus redistribution" or "real-time AI electricity sharing".
The best outcome may be to recommend individual self-consumption for some roofs, collective allocation for others, or no viable investment under a scenario. Avoid pre-selecting a favorable result.

C. GROUND TRUTH VS MODEL VS SYNTHETIC — STRICT LABELS
================================================================================

Define a provenance field for every data source and result:
  OBSERVED_METER: real measured electricity series, with building and temporal provenance.
  OBSERVED_AGGREGATE: real area/sector or grid-level totals, NOT individual building labels.
  OFFICIAL_GEO: building footprints or cadastral metadata.
  OFFICIAL_CERTIFICATE: modeled energy certificates, NOT actual hourly consumption.
  ESTIMATED_ROOF: modeled map/geometry-based PV potential, NOT as-built/structural approval.
  SIMULATED_PHYSICS: PVGIS/CEA/EnergyPlus outcomes from models and assumptions.
  SYNTHETIC_SCHEDULE: manually defined occupancy or operation patterns.
  ML_PREDICTION: inference from a trained surrogate/model.
  HYPOTHETICAL_ALLOCATION: agreement/benefit scenario with no real-world contract.
  FINANCIAL_ASSUMPTION: tariff/capex/O&M scenario with source and date.
  EMISSIONS_ASSUMPTION: grid factor and associated year/system boundary.

Never label simulated, scenario or predictive values as "actual building consumption" or "actual CO2 saved". Avoid falsely precise results. A historic public meter reference from a foreign building is a legitimate training target but is NOT a Barcelona meter.

H. HOURLY ENERGY, ECONOMIC AND SOCIAL CALCULATIONS
================================================================================

Unit and time discipline:
- Use an explicit base time index and clear time zone convention (Europe/Madrid, plus UTC normalization for DST). Prevent duplicate/missing hours when switching from local time.
- Normalize both PV and demand to kWh PER HOUR before matching.
- If historical BDG2 meter year differs from PVGIS weather/output year, develop a reproducible representative-year alignment method (calendar/day-type/week/season or same-calendar simulation), not an unqualified chronological join.
- Distinguish power kW, installation peak kWp, and energy kWh. Do not confuse total final energy with electricity.
- PVGIS may report hourly POWER conventions; inspect actual exported schema and units before calling values hourly kWh.

Simplified allocation per hour h:
    P[h] = host PV electricity generated [kWh]
    L[i,h] = demand of participant i [kWh]
    beta[i,h] = agreed allocation coefficient for participant i (non-negative, with coefficient sum meeting the modeled settlement rule)
    allocated_pv[i,h] = beta[i,h] * P[h]
    used_pv[i,h] = min(allocated_pv[i,h], L[i,h])
    grid_import[i,h] = max(0, L[i,h] - allocated_pv[i,h])
    unconsumed_allocated_pv[i,h] = max(0, allocated_pv[i,h] - L[i,h])
These are simplified planning calculations; verify actual statutory billing/compensation and grid access rules before describing them as an official legal settlement.

SCENARIOS TO COMPARE

  B) host-only PV self-consumption (individual reference)
  C) fixed-share collective allocation
  D) AI-informed demand-matched PRE-AGREED hourly allocation schedule
Important: distinguish C vs D effect (AI value) and B vs C effect (collective value). Same PV generation and same demand must be used in all alternatives.

# Roofscapes (Re)Powered V2 — Implementation Pipeline

**Studio constraint:** Post-midterm; approximately four-to-five weeks remain as of November 14, 2026. **One** final Barcelona building cluster, **one** primary trained AI model, transparent impact evaluation. The tool is a **pre-installation design support prototype**, not a live energy-community controller.

## Central research question

How can AI-assisted electricity-demand estimation guide the use and distribution of limited rooftop solar production among a small group of Barcelona buildings, subject to preliminary environmental, economic and social constraints?

## Stage 0 — Define test and data definitions (day 1)
- **Inputs:** Study objective, required metrics, permitted time frame, geographic scale.
- **Work:** Freeze one host + three to five consumer buildings; choose all timestamps in one convention (Europe/Madrid local with UTC normalization and DST handling); distinguish electricity from thermal demand; specify data provenance.
- **Tools/precedents:** Barcelona Energy Resources Map; Spanish collective self-consumption framework.
- **Outputs:** `inputs/building_cluster.csv`, `inputs/host_roof.csv`; model target defined as hourly **electricity kWh**.
- **Gate:** Selected host can plausibly accommodate PV; participant eligibility and participation are described as hypothetical if unverified.

## Stage 1 — Download and audit datasets (days 1–3)
- **Inputs:** Public catalogs, Building Data Genome 2 (BDG2), Barcelona electricity, Catalonia certificates/PV registry, Catalonia hourly demand.
- **Work:** Run `download_datasets.py`; audit schema, completeness, site types, units, timezones, licensing and access failures. Select relevant office/retail/institutional BDG2 electricity meters. Do **not** use Catalonia hourly system demand as building-level labels.
- **Tools/precedents:** BDG2 (Miller et al., Scientific Data 2020); pandas; Barcelona Open Data; ICAEN certificates.
- **Outputs:** `raw/*`, `processed/data_quality_report.csv`, `processed/train_buildings.csv`, `processed/train_meter_hourly.csv`.
- **Gate:** Have real electricity targets and building metadata with consistent IDs; document unavailable variables.

## Stage 2 — Select and describe the Barcelona cluster (days 3–5)
- **Inputs:** Barcelona Solar Map, actual host characteristics, Cadastre or existing building inventory, energy certificates, published opening hours.
- **Work:** Choose one PV host roof and 3–5 consumers; record area/type, source, operating hours and assumptions. Use available PV area/capacity instead of repeating rooftop vision/segmentation training.
- **Tools/precedents:** Barcelona municipal solar atlas; Cadastre INSPIRE; Barcelona municipal shared-self-consumption service.
- **Outputs:** `inputs/building_cluster.csv`, `inputs/host_roof.csv`, `inputs/source_register.csv`.
- **Gate:** A plausible cluster with known coordinates, use types and estimated PV capacity.

## Stage 3 — Generate PV output from established tool (days 5–7)
- **Inputs:** Host location, installed kWp, panel tilt/azimuth/losses, selected PVGIS weather or time series.
- **Work:** Export hourly PV output with the **PVGIS web UI**, record configuration and time basis. Validate annual yield order of magnitude against the Barcelona Solar Map. No new PV AI training.
- **Tools/precedents:** European Commission JRC PVGIS 6; pvlib **only if** user-configurable PV modeling proves essential.
- **Outputs:** `processed/pv_hourly.csv`, `inputs/pvgis_assumptions.csv`, provenance and uncertainty note.
- **Gate:** Hourly kWh generation properly normalized to selected roof's kWp and timezone. Distinguish actual weather year from typical year.

## Stage 4 — Define controllable building-use scenarios (days 6–9)
- **Inputs:** Selected building uses and area, public opening hours, BDG2 benchmark shapes, optional CEA/DOE archetypes.
- **Work:** Build **manual, editable** office / residential / retail / institutional schedules; weekdays vs weekends; low/base/high activity and weather-sensitive loads. Document synthetic assumptions. Do not invent 'true' meter readings for the case study.
- **Tools/precedents:** City Energy Analyst (CEA); EnergyPlus schedule semantics; DOE End-Use Load Profiles (only for cross-check, not Barcelona ground truth).
- **Outputs:** `synthetic/operation_schedules.csv`, scenario definitions, `processed/demand_scenario_reference.csv`.
- **Gate:** At least 3 coherent scenarios per selected use, with annual consumption plausibility ranges.

## Stage 5 — Train one AI model (days 7–14)
- **Inputs:** BDG2 measured hourly electricity, joined building metadata/weather and calendar features; **or** CEA simulated hourly loads with known operating schedules (alternative, not an additional requirement).
- **Work:** Fit an **XGBoost regressor** for hourly electricity demand in kWh (optionally normalize by floor area). Compare against hour-of-week and seasonal baseline. Hold out entire buildings and evaluate multiple periods. For use without a building's historical meter, only use features available at inference time.
- **Tools/precedents:** BDG2; XGBoost; scikit-learn. **Alternative:** CEA + XGBoost simulation surrogate if scenario controllability is central.
- **Outputs:** `models/demand_xgboost.joblib`, `results/model_metrics.csv`, `processed/demand_hourly.csv`, feature/spec documentation.
- **Gate:** Model improves meaningful baseline **on held-out buildings or simulation configurations**. Report MAE/RMSE and known transfer limitations; if it does not improve baseline, revise target or use baseline honestly.
- **CRITICAL:** BDG2 has no observed building occupancy schedule features; do not imply XGBoost learned schedule response if schedules were not part of training. CEA surrogate is the alternative route when schedule effects must be learned explicitly.

## Stage 6 — Compute rooftop solar-demand matching (days 13–18)
- **Inputs:** `pv_hourly.csv`, `demand_hourly.csv`, proposed sharing coefficients and participant definitions.
- **Work:** Evaluate host-only solar; fixed-share collective allocation; demand-informed **pre-agreed** hourly allocation profiles. ## Why no authenticated API?

- ESIOS is **excluded**.
- The Catalonia datasets have **public, anonymous CSV download links** that happen to use `/api/v3/` in the publisher's URL. The script only retrieves files; it does not use authenticated APIs, live connections, API tokens or credentials.
- PVGIS site-specific solar output requires a known roof location/capacity, so it is **not** automatically downloaded. Use PVGIS in its web UI and export the hourly output as a file.
- Red Eléctrica emissions and electricity-price assumptions should be saved as documented offline references, rather than relying on a continuously updating service.

## Limitations and practical notes

- Building Data Genome 2 is measured data, but **not a Barcelona building-meter dataset**. It covers 2016–2017 non-residential sites and must be evaluated for transfer bias.
- Some GitHub BDG2 files use Git Large File Storage (LFS). If normal direct download provides only a pointer, the script attempts a Git LFS fallback if **Git for Windows + Git LFS** are installed. If not, use the repo website and download the files manually.
- The Catalonia certificates export is for all Catalonia and can be large. Filter for Barcelona **after download** once the actual schema has been inspected. Never infer field names without inspection.
- Barcelona municipal PV and Barcelona electricity portals may disallow script requests even though public CSV downloads are listed; use their public dataset pages if the script logs `HTTP 403`.
- Public certificates are energy-performance indicators, **not hourly measured electricity**.
- User-defined occupancy patterns are synthetic assumptions. Train/validate using held-out buildings or held-out simulation configurations; do not present synthetic test scores as empirical real-building accuracy.
